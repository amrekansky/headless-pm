> **Command prefix:** Claude and Gemini use `/skill-name`. Codex uses `$skill-name`. All skill names are the same across all three CLIs.

## Setup & Workspace

| Skill | Description | When to use | Example prompt |
|-------|-------------|-------------|----------------|
| `/pm-onboarding`<br>Codex: `$pm-onboarding` | First-time PM workspace setup. Runs an 8-question interview to understand your product, team, and current focus, then creates `.pm/STATE.md` with your full context. Optionally reads existing PRDs, roadmaps, or backlogs to populate the workspace automatically. | **Run once after install.** First command to type when you open your CLI for the first time. | `/pm-onboarding` |
| `/pm-chat`<br>Codex: `$pm-chat` | Conversational workspace capture — write anything in natural language (meeting notes, decisions, risks, stakeholder updates) and the skill extracts structured data into the correct `.pm/` files automatically. No special syntax or format required. | When you want to capture context quickly after a meeting, call, or slack thread without thinking about which file to update. | `/pm-chat Just had a call with the CPO. Decision: deprioritize mobile for Q3. Risk: 3 enterprise customers expecting mobile by June.` |
| `/pm-review`<br>Codex: `$pm-review` | Weekly workspace health check. Sweeps all `.pm/` files for stale risks, overdue open questions, decisions without implementation markers, and stakeholders without recent contact. Outputs a prioritized action list. | Every Monday or Friday. Run before sprint planning to make sure your context is current. | `/pm-review` |
| `/pm-radar`<br>Codex: `$pm-radar` | Situational awareness agent. Reads MCP-connected sources (Notion, Jira, Linear) plus your `.pm/` workspace and synthesizes the current project state into `.pm/situation.md`. Feeds downstream orchestrated workflows. | Before running any multi-step workflow or at the start of a new week. | `/pm-radar` |
| `/pm-save`<br>Codex: `$pm-save` | End-of-session wrap-up. Updates `context.md`, `STATE.md`, `goals.md`, `decisions.md`, `risks.md`, and commits everything to git. Preserves full session context so the next conversation picks up exactly where you left off. | At the end of every Claude/Gemini/Codex session where you made decisions or produced artifacts. | `/pm-save` |
| `/pm-agents`<br>Codex: `$pm-agents` | PM subagent hub. Lists all 8 domain subagents with descriptions, or routes you to the right one based on what you're working on. | When you know you need a deep workflow but aren't sure which domain subagent to invoke. | `/pm-agents I need to understand why our activation rate dropped` |

## Discovery

| Skill | Description | When to use | Example prompt |
|-------|-------------|-------------|----------------|
| `/pm-discover`<br>Codex: `$pm-discover` | Full discovery phase wizard. Guides you through problem framing → hypothesis generation → customer interview design → synthesis → go/no-go decision. Structured around the dual-track agile discovery loop and Teresa Torres's continuous discovery principles. Outputs a discovery brief with confidence levels. | When starting any new feature or initiative where the problem is not yet well-defined. | `/pm-discover Our B2B customers are churning at 8% monthly. We think onboarding is the issue but aren't sure.` |
| `/pm-discovery`<br>Codex: `$pm-discovery` | Discovery orchestration subagent. Runs a full discovery cycle by sequencing cusdev → pm-jtbd → pm-persona → pm-hypothesis → pm-metrics automatically. Each artifact feeds the next. | When you want a complete, end-to-end discovery run with minimal manual coordination. | `/pm-discovery New initiative: add collaboration features to our solo-user SaaS` |
| `/cusdev`<br>Codex: `$cusdev` | Customer discovery session using Mom Test principles (Rob Fitzpatrick). Produces an interview guide that avoids leading questions, extracts real buying behavior, and surfaces unmet jobs-to-be-done. Includes a synthesis framework for patterns across multiple sessions. | Before building any new feature. Before validating a hypothesis. When you have an assumption that needs real customer evidence. | `/cusdev I think our users are struggling with onboarding because the setup takes too long. I have 3 interviews this week.` |
| `/pm-hypothesis`<br>Codex: `$pm-hypothesis` | Generate and prioritize testable product hypotheses from a problem statement or strategic goal. Structures hypotheses using the "We believe / For / Because / We'll know when" format. Ranks by impact × confidence to surface the most valuable tests. | Before starting a discovery sprint. When you have a strategic goal and need to decide what to investigate first. | `/pm-hypothesis We want to improve D7 retention for new users. What should we investigate?` |
| `/pm-jtbd`<br>Codex: `$pm-jtbd` | Map Jobs-to-be-Done from customer research or intuition using the Christensen/Ulwick lens. Produces structured JTBD statements with functional, social, and emotional dimensions. Links jobs to existing product features and reveals underserved gaps. | After running customer interviews. When reframing a problem that has been over-specified as a solution. | `/pm-jtbd Here are notes from 5 customer interviews: [paste notes]. What are the core jobs?` |
| `/jtbd-interview`<br>Codex: `$jtbd-interview` | Run a Jobs-to-be-Done interview using the Christensen/Ulwick framework. Produces the full interview question sequence and a synthesis template that maps to JTBD statements. Focuses on the "hire/fire" moment of switching to a new solution. | When you want to understand why customers choose your product — not just what they use it for. | `/jtbd-interview I'm interviewing a user who signed up last month after switching from Notion.` |
| `/switch-interview`<br>Codex: `$switch-interview` | Conduct a JTBD Switch Interview using Bob Moesta's timeline methodology. Uncovers the exact sequence of events, emotions, and forces that led a customer to switch from their old solution to yours — or away from yours to a competitor. | When you want to understand true buying triggers and design better acquisition or retention messaging. | `/switch-interview I'm interviewing a customer who switched to us from Salesforce 6 months ago.` |
| `/pm-persona`<br>Codex: `$pm-persona` | Synthesize user research into an evidence-based product persona. Unlike fictional personas, this builds from actual interview data and behavioral patterns. Includes JTBD alignment, pain points, success metrics, and anti-patterns. | After completing 3+ customer discovery interviews. Before writing a PRD or designing a feature. | `/pm-persona Here are notes from 6 interviews with operations managers: [paste notes]` |
| `/assumption-mapping`<br>Codex: `$assumption-mapping` | Map assumptions on a criticality × uncertainty grid to identify the Riskiest Assumption to Test (RAT). Uses the Two-by-Two framework to separate assumptions that need immediate testing from those that can be validated later in the cycle. | Before committing to a solution. During discovery to prioritize what to test first. | `/assumption-mapping We're planning to build a self-serve analytics dashboard. Here are our assumptions: [list]` |
| `/opportunity-solution-tree`<br>Codex: `$opportunity-solution-tree` | Build an Opportunity Solution Tree using Teresa Torres's continuous discovery framework. Maps the desired outcome → opportunities → solutions → experiments in a visual hierarchy. Ensures product solutions are directly connected to customer outcomes. | When planning a discovery sprint or when teams are building solutions without clear outcome alignment. | `/opportunity-solution-tree Desired outcome: increase trial-to-paid conversion from 12% to 20%. Here's what we know from research: [paste]` |
| `/continuous-interview-synthesis`<br>Codex: `$continuous-interview-synthesis` | Synthesize insights from multiple continuous discovery interviews (Teresa Torres). Identifies patterns across sessions, updates the opportunity solution tree, and surfaces the strongest signal for the next sprint. | Weekly, after the recurring interview cadence. Scales the insight from individual conversations to team-level decisions. | `/continuous-interview-synthesis Here are notes from this week's 3 interviews: [paste notes]` |
| `/pm-survey`<br>Codex: `$pm-survey` | Design a quantitative survey for product research. Produces survey questions with branching logic, Likert/NPS/binary scales, and an analysis plan. Avoids common survey design failures like leading questions and double-barreled items. | After qualitative discovery to validate patterns at scale. Before roadmap planning when you need quantified signal. | `/pm-survey We think enterprise customers struggle with our permission model. Design a survey to validate this for our 500-person user base.` |

## Customer Research

| Skill | Description | When to use | Example prompt |
|-------|-------------|-------------|----------------|
| `/customer-research`<br>Codex: `$customer-research` | Customer Research PM subagent. Orchestrates 13 interview and segmentation skills automatically — from interview design through synthesis to persona creation. Routes to individual skills or runs the full research sequence. | When starting a major research initiative and want end-to-end orchestration. | `/customer-research Run a full customer research cycle for our SMB segment` |
| `/user-segmentation`<br>Codex: `$user-segmentation` | Segment users by behavioral and demographic attributes to sharpen product decisions. Identifies distinct groups with different needs, value levels, and growth potential. Outputs a segmentation matrix with strategic implications for each segment. | Before persona creation or roadmap prioritization. When one-size-fits-all product decisions feel wrong. | `/user-segmentation Here are our active users by plan, tenure, and usage patterns: [data]. Help me segment them.` |

Based on psychographic segmentation methods. Reveals why different customers respond differently to the same product — even when their demographics are identical. | When demographic segments show no behavioral difference. When trying to understand why NPS varies among similar users. | `/attitudinal-segmentation Our mid-market customers look the same demographically but some love us and some churn. Here's survey data: [paste]` |
| `/icp-definition`<br>Codex: `$icp-definition` | Define the Ideal Customer Profile (ICP) with firmographic, behavioral, and psychographic attributes. Builds a scoring rubric to qualify leads and focuses product investment on the customers most likely to generate long-term value. | Before building a sales motion, targeting campaigns, or deciding which customer requests to prioritize. | `/icp-definition We have 200 customers. Our best 20 have these traits: [list]. Help me define and codify our ICP.` |
| `/pm-segmentation-synthesis`<br>Codex: `$pm-segmentation-synthesis` | Synthesize patterns from multiple customer research sessions into actionable customer segments with JTBD profiles and attitudinal dimensions. Connects qualitative interview data to quantitative usage patterns. | After completing a batch of 5+ interviews. When preparing for a segment-driven roadmap review. | `/pm-segmentation-synthesis Here are notes from 10 enterprise interviews and our usage data export: [paste]` |
| `/pm-nps-csat`<br>Codex: `$pm-nps-csat` | Analyze NPS and CSAT survey data to identify root causes, segment dissatisfied users, and surface the highest-leverage improvements. Produces roadmap impact recommendations with supporting evidence from verbatim responses. | After collecting an NPS/CSAT survey batch. When NPS dropped and you need to understand why. | `/pm-nps-csat Our NPS dropped from 42 to 31 this quarter. Here are 200 responses: [paste]` |
| `/funnel-analysis`<br>Codex: `$funnel-analysis` | Analyze conversion funnel stages from awareness through activation to retention. Identifies the biggest drop-off points, quantifies revenue impact, and prioritizes fixes by effort-to-impact ratio. | When conversion rate declines or when preparing a growth sprint. | `/funnel-analysis Our funnel: signup 10k → activation 3k → paid 800 → retained 30d 600. Help me find and prioritize the biggest opportunity.` |
| `/growth-loops`<br>Codex: `$growth-loops` | Map product growth loops to identify compounding acquisition and retention mechanisms. Distinguishes viral loops, content loops, and product-led loops from linear marketing funnels. Outputs a loop diagram with leverage points and experiment ideas. | When optimizing for sustainable, compounding growth rather than paid acquisition. | `/growth-loops We're a B2B SaaS. Our users share reports externally. Help me map our viral loop and find leverage points.` |
| `/feedback-triage`<br>Codex: `$feedback-triage` | Categorize and prioritize incoming user feedback by theme, impact, and frequency. Extracts signal from noise across support tickets, reviews, NPS verbatims, and sales calls. Produces a prioritized theme report with evidence links. | Weekly to keep the backlog signal-driven. After a batch of support tickets or interview notes lands. | `/feedback-triage Here are 50 support tickets from this week: [paste]. What are the top themes?` |
| `/pm-cluster`<br>Codex: `$pm-cluster` | Feedback clustering agent. Reads all `.pm/artifacts/interview-*.md` files, groups signals into themes using semantic clustering, and outputs a structured clusters report. Surfaces patterns across dozens of conversations automatically. | After accumulating 5+ interview files in your workspace. Replaces manual affinity mapping. | `/pm-cluster` |
| `/pm-customer-health`<br>Codex: `$pm-customer-health` | Build a customer health scoring model for B2B accounts. Identifies at-risk accounts based on usage, engagement, and support signals. Produces escalation briefs for CSM and informs retention roadmap priorities. | When managing a B2B portfolio. Before a quarterly business review. When churn is accelerating. | `/pm-customer-health We have 80 enterprise accounts. Here's our usage and support data: [paste]. Who's at risk?` |

## Strategy & Vision

| Skill | Description | When to use | Example prompt |
|-------|-------------|-------------|----------------|
| `/strategy`<br>Codex: `$strategy` | Strategy PM subagent. Routes to 13 strategy and vision skills, or runs the full strategy sequence automatically — vision → positioning → roadmap → OKR alignment. | When starting a strategy cycle or when multiple strategy questions need to be tackled together. | `/strategy Run a full strategy review for Q3 planning` |
| `/vision-setting`<br>Codex: `$vision-setting` | Craft a product vision statement that aligns the team on a 3-5 year future state. Uses the structure of inspiring vision statements (customer outcome + product role + differentiation). Helps distinguish vision from strategy and features. | When starting a new product, after a pivot, or when the team has lost strategic alignment. | `/vision-setting Our product is an AI-powered PM tool. Our users are PMs at fast-growing startups. Help me write a 3-year vision.` |
| `/strategy-stack`<br>Codex: `$strategy-stack` | Build or audit the Product Strategy Stack — the vertical alignment from company mission → vision → strategy → OKRs → roadmap. Identifies gaps, contradictions, and misalignments between levels. | At the start of annual planning. When roadmap decisions keep getting questioned by leadership. | `/strategy-stack Here's our mission, vision, and current roadmap: [paste]. Is our strategy coherent?` |
| `/pm-metrics`<br>Codex: `$pm-metrics` | Define a complete metrics framework: North Star metric, L1 input metrics, L2 leading indicators, and guardrail metrics. Based on Cagan's outcome-driven product model. Prevents teams from optimizing vanity metrics at the expense of real value. | When forming a new product team. When metrics are unclear, contested, or disconnected from strategy. | `/pm-metrics We're building a B2B collaboration tool. Our goal is engagement. Help me define our full metrics stack.` |
| `/north-star-selection`<br>Codex: `$north-star-selection` | Select the single North Star Metric that best captures the value your product delivers to customers. Evaluates candidate metrics against the criteria: reflects customer value, predicts long-term retention, is actionable by the team. | When establishing a new metric framework or when the team debates which metric to optimize. | `/north-star-selection We're a marketplace for freelance designers. Candidates: GMV, jobs posted, jobs completed, repeat hire rate. Help me choose.` |
| `/pm-okr`<br>Codex: `$pm-okr` | Set and track OKRs for a product team. Runs a quarterly OKR planning session or mid-quarter check-in. Produces structured OKR docs with confidence levels, key results status, and blockers. | At the start of each quarter. When OKRs feel disconnected from real work or are tracking the wrong outcomes. | `/pm-okr Q3 planning. Our company goal is to grow ARR by 40%. My team owns activation. Help me set team OKRs.` |
| `/pm-roadmap`<br>Codex: `$pm-roadmap` | Build a strategic roadmap from competing initiatives. Orchestrates pm-prioritize → pm-stakeholder → pm-positioning to produce a sequenced, outcome-driven plan with stakeholder alignment. Outputs in Now/Next/Later or quarterly format. | During quarterly planning. When the roadmap is full of features with no clear connection to outcomes. | `/pm-roadmap We have 12 competing requests for Q3. Here's the list with context: [paste]. Help me build the roadmap.` |
| `/pm-goals`<br>Codex: `$pm-goals` | Live goals layer for `.pm/goals.md`. Maintains Objectives as a verifiable definition-of-done and checks work against active goals — surfacing drift (work advancing no goal), orphan goals (no work), and stale goals (not reviewed in 14 days). Modes: dashboard, set, check. | Weekly to keep goals current, or any time you want to score a backlog, PRD, or sprint against the goals. | `/pm-goals check` |
| `/pm-loop`<br>Codex: `$pm-loop` | Agentic verify-until-done loop for any artifact. Detects the type, verifies against a type rubric (and the active goal), revises what fails, and repeats until every criterion passes or the safety cap (3) is hit — then appends a review trail. Runs in-session on Claude, Gemini, or Codex. | After producing a PRD, research synthesis, roadmap, or brief you want to hold up. | `/pm-loop` |
| `/pm-positioning`<br>Codex: `$pm-positioning` | Define product or feature positioning — target customer, market category, differentiation, and value proposition. Uses the classic positioning statement structure (Moore, Ries) to align product, marketing, and sales on a single message. | Before GTM planning, landing page copy, or when a new competitor has entered the market. | `/pm-positioning We're launching an AI meeting notes feature. Our competitors are Otter.ai and Fireflies. Help me position it.` |
| `/positioning-five-component`<br>Codex: `$positioning-five-component` | Define product positioning using April Dunford's 5-component framework from "Obviously Awesome": competitive alternatives, unique attributes, value themes, target customers, and best-fit market category. Produces copy-ready positioning that salespeople can actually use. | Before writing landing pages, pitch decks, or sales scripts. When existing positioning is vague or feature-led. | `/positioning-five-component Our product is headless-pm. Main competitors: PM Brain, PM Copilot. Help me run the 5-component positioning exercise.` |
| `/product-work-levels`<br>Codex: `$product-work-levels` | Classify product work across outcome levels: feature-level (builds the thing), product-level (grows the metric), company-level (changes the strategy). Based on Shreyas Doshi's LNO framework. Ensures teams work at the right level of abstraction. | During sprint planning or strategy reviews when the team is busy but outcomes aren't moving. | `/product-work-levels Here's our sprint backlog: [paste]. Help me classify each item by outcome level.` |
| `/ansoff-matrix`<br>Codex: `$ansoff-matrix` | Map growth strategies on the Ansoff Matrix — market penetration, market development, product development, and diversification. Evaluates risk and resource requirements across growth options to inform strategic bets. | During annual planning or growth strategy reviews. When the growth path is unclear or debated by leadership. | `/ansoff-matrix We're a project management tool at $5M ARR. Here's our current strategy: [paste]. Map our growth options.` |
| `/swot-analysis`<br>Codex: `$swot-analysis` | Run a SWOT analysis (Strengths, Weaknesses, Opportunities, Threats) for a product, team, or strategic decision. Produces a prioritized matrix with strategic implications — not just a list. | Quarterly or before major pivots. When preparing for a board meeting or investor review. | `/swot-analysis Analyze our product for Q3 strategy planning. Context: [paste key facts about your product and market]` |
| `/pestle-analysis`<br>Codex: `$pestle-analysis` | Analyze macro-environment factors using the PESTLE framework (Political, Economic, Social, Technological, Legal, Environmental). Surfaces external risks and opportunities that internal strategy analysis misses. | For market entry decisions, annual strategy reviews, or when external forces are creating uncertainty. | `/pestle-analysis We're planning to expand into the EU healthcare market. Run a PESTLE to surface risks and blockers.` |
| `/beachhead-mapping`<br>Codex: `$beachhead-mapping` | Identify and validate the beachhead market using Geoffrey Moore's Crossing the Chasm framework. Evaluates candidate early segments on accessibility, size, willingness to pay, and reference potential. Prevents the "boil the ocean" GTM mistake. | When deciding which early segment to win first. Before committing a sales and marketing budget to a broad market. | `/beachhead-mapping We're an AI operations tool. Candidate first segments: fintech ops teams, e-commerce ops, healthcare admin. Help me choose.` |
| `/pre-mortem`<br>Codex: `$pre-mortem` | Run a structured pre-mortem to surface risks before a launch or major decision. Imagines the project has failed, then works backward to identify causes. Produces a prioritized risk register with mitigations. | 1-2 weeks before any significant launch or commitment. When the team is too optimistic about a plan. | `/pre-mortem We're launching our enterprise tier in 3 weeks. Run a pre-mortem. Here's the plan: [paste]` |

## Execution & Delivery

| Skill | Description | When to use | Example prompt |
|-------|-------------|-------------|----------------|
| `/execution`<br>Codex: `$execution` | Execution PM subagent. | `/pm-define`<br>Codex: `$pm-define` | Definition phase wizard. Full definition cycle in one command. | After a discovery GO decision, when translating validated insights into buildable work. | `/pm-define We validated that users need bulk export. Here's the discovery brief: [paste]. Run the full definition phase.` |
| `/pm-plan`<br>Codex: `$pm-plan` | Planning phase wizard. Takes a signed-off backlog and produces a sprint-ready plan — OKR alignment → roadmap → capacity check → sprint plan → backlog grooming. Covers one quarter or one sprint depending on scope. | After definition sign-off or when starting a new planning cycle. | `/pm-plan Q3 planning. Signed-off backlog: [paste]. Team: 4 engineers, 1 designer. Run full planning phase.` |
| `/pm-sprint`<br>Codex: `$pm-sprint` | Orchestrate a full sprint cycle — capacity planning → backlog grooming → sprint planning → daily standups → demo → retro. Sequences all execution skills automatically and produces artifacts at each stage. | When you want to run an entire sprint with minimal manual coordination between skills. | `/pm-sprint New sprint. Team: 6 engineers. Carry-overs: 3 items. Deadline: feature X by end of sprint.` |
| `/pm-capacity`<br>Codex: `$pm-capacity` | Calculate team capacity for a sprint. Accounts for PTO, ceremonies, on-call rotations, and realistic throughput. Produces a capacity number with confidence range and assumptions. | Before every sprint planning session. When the team consistently over-commits. | `/pm-capacity 2-week sprint. Team: 4 engineers. PTO: Ana 2 days, Raj 0 days. Ceremonies: 4h total. What's our capacity?` |

| `/pm-story`<br>Codex: `$pm-story` | Write user stories in standard format with full acceptance criteria. Optionally generates a story map for an entire user workflow. Outputs directly to Jira or Linear. | When converting discovery findings or PRD sections into sprint-ready tickets. | `/pm-story Write stories for the onboarding flow redesign. Users: new signups. | `/pm-epic`<br>Codex: `$pm-epic` | Decompose an epic into features and user stories. Estimates total effort, identifies cross-team dependencies, and flags the critical path.
